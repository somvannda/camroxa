# "Change Run Folder & Resume" left already-submitted songs stuck retrying the old folder forever

**Date:** 2026-08-01
**Status:** implemented (fix built into desktop v1.0.11, pending user install)

## Summary

A user ran "Change Run Folder & Resume" on two Progress rows (`bass-drive`,
`beattok-remixes`) after their `E:\` drive ran out of space, but the desktop
app kept logging `Not enough free disk space to download MP3, skipping:
E:\SUNO\...` every ~5 seconds, forever, for both channels — even though the
row's run folder had already been moved. Root cause: the recovery flow
re-downloaded each song's audio into the new folder locally, but never told
the server the song was now downloaded at the new location, so the
account-wide background download sync kept reading each song's **stale,
per-song-snapshotted** `output_dir_ok`/`output_dir_alt` (still pointing at
the old, full drive) and retried it on an infinite loop.

## Product impact

**Before:** After "Change Run Folder & Resume", a batch/channel with any
songs that were generated by Suno but never successfully downloaded (e.g.
because the original drive filled up mid-batch) would have those specific
songs permanently stuck — the app would spam "Not enough free disk space"
for the *old* folder path forever, once per song per ~5s poll cycle, even
though the row's run folder had moved and had free space. The only user-facing
symptom was runaway error-log spam; no new folder/files were ever created at
the new location for these specific songs.

**After:** Running "Change Run Folder & Resume" now also updates each
song's tracked download state (`downloaded_ok`/`downloaded_alt` and
`output_dir_ok`/`output_dir_alt`) to point at the new folder, whether the
re-download during recovery succeeded or failed. The background sync now
either sees the song as done, or retries it against the *correct* (new)
folder instead of the dead one.

## Technical impact

`output_dir_ok`/`output_dir_alt` on a Suno task row is a **snapshot** taken
once at Suno-submission time from the batch's run_dir at that moment
(`BatchService._resolve_batch_run_dir`) — it is not a live pointer to the
batch's current run_dir. `sync_local_progress_from_desktop` (used by the
folder-change flow to repoint the row) only updates `batch_channel_assets`
(image manifests + `pipeline_complete`), never the per-song Suno task rows.
So any song already submitted to Suno before the folder change — regardless
of whether its download had previously succeeded — kept its original,
now-stale `output_dir_ok`/`output_dir_alt`, and the always-running
`MusicDownloadSyncWorker` background poller (reads `list_pending_suno_downloads`,
keyed off `downloaded_ok`/`downloaded_alt` + those same stale dirs) retried
it against the old folder on every poll, forever, since nothing ever marked
it downloaded or moved its tracked path.

`RunFolderRecoveryWorker.run()` (desktop) now builds a `MusicDownloadSyncItem`
for every song in `build_batch_redownload_plan`'s response (regardless of
whether its own re-download attempt succeeded) and calls
`PlatformApi.sync_music_downloads(...)` once at the end of the MP3 phase,
setting:
- `downloaded_primary`/`downloaded_secondary` = whether the re-download into
  the new folder succeeded (role-scoped: OK → primary, ALT → secondary)
- `output_dir_primary`/`output_dir_secondary` = the new run folder,
  unconditionally — even on a failed re-download, so a *subsequent* retry
  by the background sync targets the new (working) folder instead of the
  dead one, rather than hammering the old path indefinitely.

No backend changes were required — `POST /music/downloads/sync` already
supported updating `output_dir_*` independently of `downloaded_*` via
`BatchRepository.update_suno_download_state`'s `COALESCE` semantics.

## Files touched

- `camxora_python/shared/workers/data_workers.py` — `RunFolderRecoveryWorker.run()`
  now syncs `output_dir_*`/`downloaded_*` state back to the server for every
  song in the redownload plan, success or failure.
- `camxora_python/tests/test_run_folder_recovery_worker.py` — new/updated
  assertions covering: sync called with correct primary-role fields on
  success, sync still repoints `output_dir` on a failed re-download (so the
  next background retry targets the new folder), and a new test for the
  ALT-role case (must update `_secondary` fields, not `_primary`, so it
  doesn't clobber the other channel's tracked state).
- `camxora_python/pyproject.toml`, `camxora_python/resources/app-version.txt`,
  `camxora_python/tests/test_app_version.py` — version bump to 1.0.11.
- `CHANGELOG.md` (root, desktop) — `[1.0.11]` entry.

## Migration / deploy

Desktop-only fix; no platform_api or database changes. Ships in the v1.0.11
production installer. No sandbox/production backend deploy needed.

## Tests

- `pytest camxora_python/tests/test_run_folder_recovery_worker.py -v` — 5
  passed (2 new/updated for the sync-state assertions, 1 new ALT-role test).
- `pytest camxora_python/tests/test_progress_view.py camxora_python/tests/test_music_download_coordinator.py -v` — 18 passed (no regressions).

## Follow-ups

- The affected user's already-running v1.0.9/v1.0.10 install needs the new
  v1.0.11 installer, then must re-run "Change Run Folder & Resume" on the
  `bass-drive` and `beattok-remixes` rows one more time (their run folder is
  already correctly moved server-side; this second run is what will finally
  stop the stale per-song retries by repointing each song's tracked state).
- Consider surfacing `mp3_failed`/`images_failed` counts more prominently in
  the recovery result banner so a user immediately sees if the new drive also
  ran out of space (rather than only discovering it via log spam again).
