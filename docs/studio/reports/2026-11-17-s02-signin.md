## 2. Backend routes used (no new backend route)

The web app's `/api/v3/*` rewrite targets `PLATFORM_API_URL` (platform_api, FastAPI), which mounts
the auth router on both `settings.api_v1_prefix` and `settings.api_v3_prefix`. Used:

| Route | Method | Payload | Behaviour |
|---|---|---|---|
| `/api/v3/auth/google/url` | GET | `?redirect_uri=<absolute>` | `200 {url, state}`; `state` is a signed state bound to the allowlisted redirect. `503 {detail: "Google sign-in is not configured."}` when `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` are empty; `422` when the redirect is not in `GOOGLE_REDIRECT_URIS`. |
| `/api/v3/auth/google/callback` | POST | `{code, state, referral_code?}` | Verifies the signed state, exchanges the code, links/creates the user, sets the session cookies, returns the token pair. |

(`platform_api/routers/auth.py` § "Google sign-in (music web)", lines 1314–1487;
`platform_api/services/google_oauth.py`.)

The browser never sees a Google client secret, and nothing talks to Google from the client.

### Callback landing

The API rejects a `redirect_uri` that is not allowlisted, so the browser origin must be registered.
Added the local canonical web app to the **default** allowlist (`platform_api/config.py`):

```
http://localhost:3103/auth/callback
http://127.0.0.1:3103/auth/callback
```

Production/sandbox still need `https://camxora.com/auth/callback` (and the existing
`music.camxora.com` entry) in `GOOGLE_REDIRECT_URIS`. This is configuration, not deploy — the
production hold stands.

New web route: `camxora.com/app/auth/callback/page.tsx` (`/auth/callback`). It reads `code`/`state`,
checks the locally stored state, posts to `/api/v3/auth/google/callback`, refreshes `AuthProvider`,
and replaces the location with the stored, same-origin `next` path. `access_denied` gets "Google
sign-in was cancelled."; any other failure renders the error plus `Back to sign in`.

### Truthful Google states

The button probes the API on mount and again on click:

- **ready** — enabled, "Continue with Google", navigates to the API URL.
- **not configured** (503) — disabled, title *"Google sign-in is not configured in this build"*,
  inline `role="status"` "Google sign-in is not configured in this build. Use email and password
  below."
- **origin not allowlisted** (400/422) — disabled, title *"Google sign-in is not enabled for this
  address"*, inline notice pointing at email sign-in.
- **API unreachable** — disabled, title *"Google sign-in is unavailable right now"*, inline notice.

No state claims Google works when the backend says it does not.

### The five inert providers

Rendered with the captured labels and marks, in the captured order:

| Provider | Label | Disabled | Reason shown (`title`, `aria-disabled`) |
|---|---|---|---|
| Apple | `Continue with Apple` | yes | "Apple sign-in is not configured in this build" |
| Phone | `Continue with Phone` | yes | "Phone sign-in is not configured in this build" |
| Discord | `Discord` | yes | "Discord sign-in is not configured in this build" |
| Facebook | `Facebook` | yes | "Facebook sign-in is not configured in this build" |
| Microsoft | `Microsoft` | yes | "Microsoft sign-in is not configured in this build" |

No handler, no hidden link, no imitation of a live control: `disabled` removes them from the tab
order, the dashed border and 0.62 opacity mark them visually, and the title states why.
There is no backend or OAuth client for these providers in this build, so wiring them would be
fiction; they are recorded here as **not configured**, not as missing.
